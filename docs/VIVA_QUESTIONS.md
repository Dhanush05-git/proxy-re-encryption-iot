# Viva Questions and Answers

## Proxy Re-Encryption for Secure IoT Cloud Data Sharing

---

### Q1. What is Proxy Re-Encryption (PRE)?

**Answer:**

Proxy Re-Encryption is a cryptographic primitive that allows a semi-trusted proxy to transform a ciphertext encrypted under Alice's public key into a ciphertext encrypted under Bob's public key, *without the proxy ever learning the plaintext*.

The proxy holds a **re-encryption key** `rk_{A→B}` derived from Alice's secret key and Bob's public key. Using this key, the proxy applies a transformation:

```
Enc(pk_A, m)  --[proxy applies rk_{A→B}]-->  Enc(pk_B, m)
```

The key security properties are:
- The proxy learns nothing about the message `m`.
- The re-encryption key `rk_{A→B}` does not reveal Alice's secret key `sk_A`.
- The re-encryption is **unidirectional**: `rk_{A→B}` cannot compute `rk_{B→A}`.
- Collusion safety: even if the proxy colludes with Bob (combining `rk_{A→B}` with `sk_B`), Alice's secret key `sk_A` remains secure.

PRE was first formally defined by Blaze, Bleumer, and Strauss (1998), and the practically secure AFGH scheme (used by Umbral) was introduced by Ateniese, Fu, Green, and Hohenberger in 2006.

---

### Q2. How does the Umbral PRE scheme work?

**Answer:**

Umbral is a **threshold proxy re-encryption scheme** based on the AFGH PRE construction, using elliptic curve cryptography on the secp256k1 / BN256 curve.

**Key generation**: Each party generates a secret key `sk ∈ Z_q` and public key `pk = g^sk` (a point on the elliptic curve).

**Encryption** (Alice encrypts DEK `m`):
1. Sample random `r ∈ Z_q`.
2. Compute `E = pk_A^r`, `V = g^r`, `s = r + H(E,V)·sk_A`.
3. Derive symmetric key `K = KDF(E)` and encrypt: `c = Enc_K(m)`.
4. **Capsule** = `(E, V, s)`. Return `(capsule, c)`.

**Key fragment generation** (Alice delegates to Bob):
1. Compute `d = H(pk_B, pk_B^{sk_A})` (combining both keys).
2. Set up polynomial `f(x) = (sk_A · d^{-1}) + a_1 x + ... + a_{t-1} x^{t-1}` over `Z_q`.
3. Evaluate at `n` points: `kfrag_i = f(x_i)`. Sign each with Alice's signing key.

**Re-encryption** (Proxy i, with `kfrag_i`):
- `cfrag_i = (E · g^{kfrag_i}, x_i, proof_i)`

**Decryption** (Bob, with ≥t cfrags):
1. Lagrange-interpolate the cfrag points to reconstruct `E' = E · g^{f(0)} = E · g^{sk_A · d^{-1}}`.
2. Compute `K = KDF((E')^{sk_B · d})` = `KDF(E^{sk_A})` (the same K Alice used).
3. Decrypt `m = Dec_K(c)`.

The elegance: Bob recovers the same symmetric key K that Alice derived, without Alice's secret key ever leaving her device.

### Q3. What is the Capsule in Umbral PRE?

**Answer:**

The **Capsule** is the compressed representation of the ephemeral key material from Alice's encryption step. It is a tuple `C = (E, V, s)` where:

- `E = pk_A^r = g^{sk_A · r}` — the ECDH key agreement point (Alice's public key raised to the ephemeral random scalar `r`).
- `V = g^r` — the ephemeral public key (the generator raised to the same scalar).
- `s = r + H(E, V) · sk_A (mod q)` — a commitment/signature binding the capsule to Alice's key.

The capsule is **public** — it is stored in the cloud alongside the AES ciphertext. By itself, it reveals nothing about the plaintext: computing `E` from `V` requires knowing `sk_A` (discrete logarithm problem), and the symmetric key `K = KDF(E)` is computationally hidden.

The capsule is what the proxy re-encrypts: it applies `kfrag_i` to transform the capsule into a cfrag that Bob can combine with his secret key to recover `K`. The capsule does not change in size regardless of the payload size, which is why re-encryption is O(1).

### Q4. What are kfrags and cfrags?

**Answer:**

**kfrags (Key Fragments)**: Re-encryption key fragments generated by Alice for a specific delegation. Each kfrag `kf_i = f(x_i)` is an evaluation of the secret-sharing polynomial whose constant term is the full re-encryption key `rk_{A→B}`. In Umbral:

```python
kfrags = generate_kfrags(
    delegating_sk=alice_sk, receiving_pk=bob_pk,
    signer=signer, threshold=2, shares=3
)
```

- 3 kfrags are generated; each proxy receives one.
- Each kfrag is signed by Alice's signing key to prevent substitution attacks.
- Any single kfrag reveals no information about the full re-encryption key (Shamir secret sharing security).

**cfrags (Capsule Fragments)**: The output of a proxy re-encryption operation. Each proxy `i` applies its `kfrag_i` to the capsule to produce `cfrag_i`:

```python
cfrag = reencrypt(capsule, kfrag)  # returns VerifiedCapsuleFrag
```

- Each cfrag is a partial transformation of the capsule.
- One cfrag alone is insufficient to decrypt (threshold property).
- Combining ≥2 cfrags (in a 2-of-3 scheme) allows Bob to reconstruct the symmetric key.

**Analogy**: Think of kfrags as "partial keys" distributed to proxy custodians. The cfrags they produce are "partial transformations" that only become useful when enough of them are combined by the authorized recipient.

### Q5. What is Threshold PRE? Why use 2-of-3?

**Answer:**

**Threshold PRE** extends standard PRE with a `(t, n)` Shamir secret sharing scheme. Instead of one proxy holding the full re-encryption key, the key is split into `n` fragments such that any `t` of them suffice to perform re-encryption.

**Why 2-of-3?**
- **Fault tolerance**: If one of the three proxy workers is offline, re-encryption still succeeds with the other two. Standard (1-of-1) PRE fails completely if the single proxy is unavailable.
- **Single-proxy security**: One compromised proxy (with 1 kfrag) learns nothing about the DEK. Only when 2 or more proxies collude can they reconstruct the full re-encryption key.
- **Trade-off**: Higher threshold (e.g., 3-of-3) increases security but reduces availability (all three proxies must be online and honest). Lower threshold (1-of-2) increases availability but reduces security margin.

**2-of-3 is the standard pragmatic choice**: It provides one fault-tolerance slot AND one security breach tolerance slot simultaneously. This is the same rationale used in multi-party computation and distributed HSMs.

### Q6. How does AES-256-GCM provide authenticity?

**Answer:**

AES-256-GCM is an **Authenticated Encryption with Associated Data (AEAD)** scheme. The "GCM" part (Galois/Counter Mode) provides both:

1. **Confidentiality**: AES-CTR mode produces a keystream XORed with the plaintext, producing ciphertext that reveals nothing about the plaintext without the key.

2. **Integrity/Authenticity**: GHASH computes a 128-bit authentication tag over the ciphertext (and optional associated data) using a polynomial over GF(2^128). The tag is appended to the ciphertext.

**On decryption**, the library recomputes the GHASH tag over the received ciphertext and compares it to the stored tag in constant time. If they differ — by even one bit — decryption fails with an `InvalidTag` exception and no plaintext is returned.

This means:
- If an attacker modifies any byte of the ciphertext, the tag check fails.
- If the nonce is different from the one used for encryption, the tag check fails.
- The tag also provides **sender authenticity** (only someone with the DEK could have produced a valid tag), but not non-repudiation (since Alice and Bob both know the DEK after re-encryption).

**In code**:
```python
aesgcm = AESGCM(dek)
# Encrypt: appends 16-byte tag
ciphertext_with_tag = aesgcm.encrypt(nonce, plaintext, None)
# Decrypt: raises InvalidTag if authentication fails
plaintext = aesgcm.decrypt(nonce, ciphertext_with_tag, None)
```

### Q7. Why can't the proxy decrypt the data?

**Answer:**

The proxy cannot decrypt the data for two independent reasons:

**Reason 1 — The proxy doesn't have the DEK**: The proxy only receives:
- The **capsule** `(E, V, s)`: three elliptic curve points, public information.
- One **kfrag** `kf_i`: a partial re-encryption key fragment.

To compute the symmetric key `K = KDF(E)`, one would need to compute `E = pk_A^r`, which requires knowing `sk_A` (discrete logarithm). The proxy has only `kfrag_i = f(x_i)`, which reveals one point on the sharing polynomial — not the secret key.

**Reason 2 — Threshold**: Even if the proxy could somehow partially reconstruct `rk_{A→B}` from its single kfrag, a single Shamir share from a 2-of-3 scheme is information-theoretically zero — it provides no information about the polynomial's constant term. This is a fundamental property of Shamir secret sharing, not a computational assumption.

**The proxy can only**: Transform the capsule into a cfrag usable by Bob. The cfrag is useless without Bob's secret key `sk_B`, which the proxy does not have.

### Q8. What happens if the proxy colludes with Bob?

**Answer:**

If one proxy (or even all three proxies) collude with Bob:
- The proxies give Bob all kfrags.
- Bob can Lagrange-interpolate to reconstruct `rk_{A→B}`.
- Bob uses `rk_{A→B}` and his `sk_B` to re-encrypt any of Alice's capsules and decrypt any delegated ciphertext.

**What Bob gains**: Access to all files for which Alice generated grants (even files he wasn't originally granted access to in the UI, if he can get the capsules).

**What Bob does NOT gain**: Alice's secret key `sk_A`. The AFGH PRE scheme is proven **collusion-safe**: `rk_{A→B} + sk_B` does not reveal `sk_A`. This is a cryptographic guarantee under the DBDH assumption.

**Practical implication**: A malicious Bob colluding with proxies is a threat but only within the scope of Alice's delegations. He cannot derive `sk_A` to forge grants, generate his own re-encryption keys, or access data from other owners.

**Mitigation**: Short-lived kfrags with expiry metadata, monitoring for unusual cfrag request patterns, and separating proxy workers to minimize trust overlap.

### Q9. How does revocation work? What are its limits?

**Answer:**

**How revocation works**:
1. Alice calls `DELETE /api/crypto/revoke/{grant_id}`.
2. The API sets `AccessGrant.status = 'revoked'` in the database.
3. All subsequent calls to `POST /api/crypto/reencrypt` check the grant status and return `403 Forbidden` if status ≠ `'active'`.
4. No new cfrags can be generated for the revoked grant.

**What revocation achieves**: Prevents any *future* re-encryption requests. After revocation, the proxy workers will not process the revoked grant's kfrags.

**The fundamental limitation — no forward secrecy**:
Cfrags already delivered to Bob before revocation are computed values that Bob can store locally. Revoking the grant cannot "un-compute" these cfrags. Bob can still use his stored `[cfrag_1, cfrag_2]` and his `sk_B` to decrypt any file for which those cfrags were generated, indefinitely.

**Why this is inherent to PRE**: The proxy's output (the cfrag) is public information from the scheme's perspective — it's a ciphertext transformation result. The access control system cannot revoke computed cryptographic values, only prevent future computations.

**Mitigation options**:
- **Key rotation**: Alice generates a new keypair and re-encrypts all files. Old cfrags become useless (they're for the old capsule/key).
- **Short-lived cfrags**: Include a timestamp commitment in the cfrag; Bob's client must refresh cfrags periodically.
- **Trusted execution environment decryption**: Bob's device fetches data through a TEE that checks revocation before allowing decryption.

### Q10. Compare PRE vs. public key encryption for data sharing.

**Answer:**

| Aspect | Public Key Encryption (naive) | Proxy Re-Encryption |
|---|---|---|
| Sharing with 10 recipients | Encrypt 10 separate copies under 10 PKs | Encrypt once, generate 10 kfrag sets |
| Storage overhead | 10× payload size | 1× payload size + small kfrag storage |
| Adding a new recipient | Re-encrypt the payload | Generate new kfrag set (~4 ms) |
| Revoking access | Re-encrypt with new key, redistribute | Delete kfrags from proxy (~1 ms) |
| Proxy sees plaintext? | Yes (must decrypt to re-encrypt) | No (transforms capsule only) |
| Owner online required? | For every access | Only for granting/revoking |
| Secret key distributed? | Must distribute to proxy | Never; proxy gets only kfrags |
| Scales to 1,000 files, 100 recipients | 100,000 re-encryptions, plaintext exposure | 100 kfrag sets, constant ciphertext |

PRE's advantages are most pronounced when:
- Data is shared with many recipients.
- Access changes dynamically (frequent grants/revocations).
- The proxy cannot be fully trusted with plaintexts.

### Q11. What is the AFGH PRE scheme?

**Answer:**

The AFGH scheme (Ateniese, Fu, Green, Hohenberger, 2006) is a **unidirectional, non-transitive, single-hop** proxy re-encryption scheme based on **bilinear pairings** over elliptic curves.

**Core idea**: Encrypt under Alice's key as `(g^r, m · e(g,g)^{r·sk_A})` where `e(·,·)` is a bilinear pairing. The re-encryption key is `rk_{A→B} = sk_A^{-1} · sk_B`. The proxy applies: `e(g^r, g^{sk_A^{-1} · sk_B}) = e(g,g)^{r·sk_B}`, transforming the second component into one decryptable by Bob.

**Security**: CCA-secure in the random oracle model under the DBDH (Decisional Bilinear Diffie-Hellman) assumption.

**Umbral's extension**: Umbral applies (t,n) Shamir secret sharing to the AFGH re-encryption key, enabling threshold re-encryption while maintaining the core security properties. It also uses a modified ECIES construction rather than a pure pairing-based approach, which gives better practical performance.

### Q12. What is the security model: honest-but-curious vs. malicious proxy?

**Answer:**

**Honest-but-curious (semi-honest) proxy**: The proxy follows the protocol correctly but tries to learn as much as possible from the data it sees. This is the standard PRE security model.

- The proxy applies `kfrag_i` to the capsule faithfully.
- It records what it sees (capsule, cfrag).
- It does not deviate from the protocol or lie about its output.

**Under this model**: Umbral is proven secure. A single honest-but-curious proxy learns nothing about the DEK or plaintext.

**Malicious proxy**: The proxy may deviate arbitrarily — produce invalid cfrags, refuse to process, replay old cfrags, or correlate requests across users.

- **Invalid cfrags**: The correctness proof embedded in each cfrag (a zero-knowledge proof in full Umbral) allows Bob to detect if a proxy applied the kfrag incorrectly. In umbral 0.3.0, verification is implicit in `VerifiedCapsuleFrag`.
- **DoS (refusal)**: Mitigated by the threshold: 1 proxy refusing still allows the other 2 to complete re-encryption.
- **Replay attacks**: Mitigated by grant status checks in the API.

**Our implementation assumes honest-but-curious proxies**, which is the standard assumption for prototype demonstrations. A production deployment would add additional audit logging, rate limiting, and cfrag correctness verification.

### Q13. Why use hybrid encryption (AES + PRE)?

**Answer:**

Hybrid encryption combines the speed of symmetric encryption with the key management advantages of asymmetric/PRE schemes.

**Why not encrypt the payload directly with PRE?**

Umbral's `encrypt()` function uses ECIES internally, which encrypts the plaintext with a stream cipher (XSalsa20 in Umbral). For large IoT payloads (1 MB+), this is significantly slower than AES-256-GCM with hardware acceleration:
- AES-NI: ~200 MB/s (hardware accelerated)
- XSalsa20 (software): ~50 MB/s typically

More critically, re-encrypting the entire payload capsule would require the proxy to process the full payload-sized capsule, making proxy operations O(payload size) instead of O(1).

**The hybrid design**:
1. AES-GCM encrypts the large payload (fast, hardware-accelerated, O(n)).
2. PRE encapsulates only the 32-byte DEK (constant time, O(1) for proxy operations).

Result: AES handles bulk encryption at 200 MB/s; PRE handles key delegation at constant 2–4 ms. This is the standard pattern used in TLS, PGP, and all production hybrid encryption systems.

### Q14. What is the role of the signing key?

**Answer:**

Alice generates an independent **signing keypair** (separate from her PRE encryption keypair) to authenticate kfrags. The signing key serves two purposes:

1. **kfrag authenticity**: Each kfrag is signed by Alice's signing key: `sig_i = ECDSA(sign_sk, kfrag_data_i)`. The proxy verifies this signature before applying the kfrag, confirming:
   - The kfrag was generated by Alice (not forged by an attacker).
   - The kfrag is intended for a specific recipient Bob (the target pk is embedded in the kfrag commitment).

2. **Anti-substitution**: Without signing, a malicious actor who intercepts the kfrag distribution could substitute a kfrag intended for Bob with one intended for Charlie, redirecting re-encryption to an unauthorized recipient. The signed kfrag binds the delegation to a specific `(alice_pk, bob_pk)` pair.

**In Umbral**: The `generate_kfrags(signer=Signer(sign_sk), ...)` call automatically signs each kfrag. The proxy's `VerifiedKeyFrag.from_bytes()` or `kfrag.verify(alice_vk, alice_pk, bob_pk)` checks the signature before `reencrypt()` is called.

### Q15. How do you detect tampering with the encrypted file?

**Answer:**

Tampering is detected at two levels:

**Level 1 — AES-GCM Authentication Tag**: The 128-bit GCM tag covers every byte of the ciphertext and the nonce. If any byte of the stored ciphertext is modified (or the nonce is changed), the GHASH computation during decryption produces a different tag. The comparison fails and `AESGCM.decrypt()` raises `cryptography.exceptions.InvalidTag`.

```python
try:
    plaintext = aesgcm.decrypt(nonce, ciphertext_with_tag, None)
except InvalidTag:
    # Data has been tampered with or key/nonce is wrong
    raise ValueError("Authentication failed: data integrity violation")
```

**Level 2 — Capsule commitment**: The Umbral capsule includes `s = r + H(E,V)·sk_A`, a Schnorr-like commitment. If the capsule bytes are modified, Umbral's internal verification during `decrypt_original` or `decrypt_reencrypted` fails.

**Level 3 — Cfrag correctness proofs**: Each cfrag includes a zero-knowledge proof that the proxy applied `kfrag_i` correctly to the capsule. An invalid cfrag (from a malicious proxy or storage corruption) causes verification failure during `decrypt_reencrypted`.

The combination means: **any tampering with the ciphertext, capsule, or cfrags is detected and results in a hard error before any plaintext is returned.**

### Q17. Explain the DEK encapsulation step.

**Answer:**

**DEK** = Data Encryption Key. It is a fresh 32-byte random symmetric key generated for each file.

**Encapsulation** means encrypting the DEK under Alice's public key using Umbral's ECIES-based encrypt function:

```python
capsule, encrypted_dek = umbral.encrypt(alice_pk, dek)
```

This call internally:
1. Generates a random ephemeral scalar `r ∈ Z_q`.
2. Computes `E = pk_A^r` (the ECDH shared secret).
3. Derives a symmetric key `K = KDF(E)` (using HKDF or similar).
4. Encrypts the DEK: `enc_dek = Enc_K(dek)` using XSalsa20 (32 bytes in, 32 bytes + overhead out).
5. Returns the capsule `(E, V, s)` and `enc_dek`.

**What is stored**: The capsule and `enc_dek` are stored in the database alongside the AES ciphertext in the filesystem. The raw DEK is **never stored** — it exists only in memory during the encryption operation.

**Why encapsulate?**: This separates the key management problem from the bulk encryption problem. The capsule enables PRE delegation — the proxy can transform the capsule without knowing what it protects (the DEK). The DEK then protects the actual payload. If Alice wants to share with Bob, she only needs to deal with the small capsule, not re-encrypt the potentially large payload.

### Q18. Why can't Charlie decrypt without a grant?

**Answer:**

Charlie (an unauthorized user) has:
- His own keypair `(sk_C, pk_C)`.
- Access to the public information: capsule, AES ciphertext.
- Valid API credentials.

**What Charlie cannot do**:

1. **Call re-encrypt directly**: The API checks that an `AccessGrant` exists with `grantee_id = Charlie` and `status = active`. No such grant exists, so the API returns `403 Forbidden` before any kfrag is accessed.

2. **Directly decrypt the capsule**: The capsule `(E, V, s)` conceals `E = pk_A^r`. Computing `E` from `V = g^r` requires knowing `sk_A` (ECDLP). Charlie doesn't have `sk_A`.

3. **Forge kfrags**: The kfrags are signed by Alice's signing key. Charlie cannot forge a valid ECDSA signature without Alice's signing secret key.

4. **Brute-force the DEK**: AES-256 has 2^256 possible keys. The best known attack (Grover's algorithm on a quantum computer) reduces this to 2^128, still computationally infeasible.

5. **Brute-force the capsule**: Equivalent to solving ECDLP on a 256-bit curve, computationally infeasible with classical computers.

The access control is enforced at both the **cryptographic level** (computational hardness) and the **application level** (grant authorization check in the API).

### Q19. What is the threshold property in detail?

**Answer:**

The threshold property in Umbral is a direct application of **Shamir's Secret Sharing** (SSS) applied to the re-encryption key.

**SSS with (t, n)**:
- A secret `s` is embedded as the constant term of a random polynomial `f(x) = s + a_1 x + ... + a_{t-1} x^{t-1}` of degree `t-1` over `Z_q`.
- `n` evaluations `(x_i, f(x_i))` are distributed as shares.
- **Any t shares suffice** to reconstruct `f` (and thus `s`) via Lagrange interpolation.
- **Any t-1 shares reveal nothing** about `s` (information-theoretic security).

**Applied to Umbral**:
- `s` = conceptually, the re-encryption key `rk_{A→B}`.
- `n = 3` kfrags are generated.
- `t = 2` kfrags are needed to re-encrypt the capsule (Lagrange combination of cfrags).
- **1 kfrag alone**: Information-theoretically zero; reveals nothing about `rk_{A→B}`.
- **2 kfrags**: Sufficient to re-encrypt. The proxies apply their kfrags independently and produce cfrags; Bob Lagrange-interpolates the cfrags to reconstruct the re-encrypted capsule point.

**Practical consequences**:
- 1 proxy offline → re-encryption still works (use remaining 2).
- 1 proxy compromised → no information leakage.
- 2 proxies collude → can re-encrypt for Bob (but not Alice → arbitrary).

### Q20. Explain capsule fragmentation.

**Answer:**

Capsule fragmentation is the process by which the proxy transforms the original Umbral capsule `C = (E, V, s)` into a **capsule fragment (cfrag)** using a kfrag.

**Step-by-step**:

1. **Input to proxy**: Original capsule `C = (E, V, s)` and kfrag `kf_i = f(x_i)` (a polynomial evaluation).

2. **Re-encryption computation**:
   ```
   cfrag_i = (E_i', x_i, proof_i)
   where E_i' = E · g^{kfrag_i}
              = g^{r · sk_A} · g^{f(x_i)}
   ```

3. **Proof generation**: The proxy generates a NIZK (non-interactive zero-knowledge) proof that it correctly applied `kfrag_i` to `E`, without revealing `kfrag_i` or `sk_A`. This proof can be verified by Bob before using the cfrag.

4. **Output**: `cfrag_i` = the transformed capsule component + evaluation point `x_i` + correctness proof.

**Bob's combination**:
Given `{cfrag_i}_{i ∈ S}` for `|S| ≥ t`:
- Lagrange interpolate: `E' = ∏_{i∈S} (E_i')^{λ_i(0)}` where `λ_i` are Lagrange coefficients.
- This reconstructs `E' = E · g^{f(0)} = E^{...} · g^{rk_{A→B}}`, the re-encrypted capsule point.
- Bob computes `K = KDF((E')^{sk_B ·d^{-1}})` = same `K` Alice used.

The fragmentation is lossless: any `t` fragments contain enough information to reconstruct the re-encrypted point, but `t-1` fragments are information-theoretically insufficient.

### Q21. How are keys serialized and transported?

**Answer:**

Umbral provides built-in serialization via the `bytes()` builtin on all cryptographic objects, and deserialization via `Type.from_bytes(data)`.

**Serialization format** (all objects are raw bytes):

| Object | Python | Size | Storage format |
|---|---|---|---|
| `SecretKey` | `bytes(sk)` | 32 bytes | base64 string in JSON |
| `PublicKey` | `bytes(pk)` | 33 bytes (compressed EC point) | base64 string |
| `Capsule` | `bytes(capsule)` | ~98 bytes | base64 string in DB |
| `VerifiedKeyFrag` | `bytes(kfrag)` | ~194 bytes | base64 string in DB (kfrags JSON array) |
| `VerifiedCapsuleFrag` | `bytes(cfrag)` | ~131 bytes | base64 string in DB / API response |

**Transport**: All base64 strings are transmitted as JSON fields over HTTP (REST API). In production, TLS ensures transport confidentiality.

**Deserialization**:
```python
import base64
from umbral import SecretKey, PublicKey, Capsule, VerifiedKeyFrag, VerifiedCapsuleFrag

sk = SecretKey.from_bytes(base64.b64decode(sk_b64))
pk = PublicKey.from_bytes(base64.b64decode(pk_b64))
capsule = Capsule.from_bytes(base64.b64decode(capsule_b64))
kfrag = VerifiedKeyFrag.from_bytes(base64.b64decode(kfrag_b64))
cfrag = VerifiedCapsuleFrag.from_bytes(base64.b64decode(cfrag_b64))
```

> [!NOTE] `VerifiedKeyFrag.from_bytes()` bypasses re-verification. In production, use `KeyFrag.from_bytes(...).verify(alice_verifying_pk, alice_pk, bob_pk)` to cryptographically confirm the kfrag before applying it in `reencrypt()`.

### Q22. What is the difference between PRE and IBE (Identity-Based Encryption)?

**Answer:**

Both PRE and IBE address delegation and key management, but differently:

| Aspect | PRE | IBE |
|---|---|---|
| Key setup | Each user has their own keypair | Requires a trusted PKG (key generator) |
| Delegation | Via re-encryption key rk_{A→B} | Key extraction from PKG for the recipient's ID |
| PKG trust | No PKG needed | PKG knows all private keys ("key escrow") |
| Recipient controls | Bob uses own sk_B | Bob's key derived from his identity by PKG |
| Revocation | Delete kfrags from proxy | Requires PKG to issue time-limited keys |
| Quantum resistance | No (ECC-based) | Some IBE schemes have post-quantum variants |

PRE is preferred when:
- Users generate their own keys (no key escrow).
- Access control must be owner-controlled without a central authority.
- The system must work offline for granting (Alice just computes kfrags; PKG not involved).

### Q23. How would you extend this system to multi-owner data sharing?

**Answer:**

For multi-owner sharing (e.g., Alice and Carol jointly own a file), the system would need:

**Option 1 — Threshold signature on kfrags**: Require both Alice and Carol to sign the kfrags before they are accepted by proxies. The proxy checks both signatures before re-encrypting.

**Option 2 — Multi-party PRE (MPRE)**: Use a PRE scheme supporting multiple delegators. The re-encryption key `rk_{AC→B}` requires both Alice and Carol's secret keys to generate. Such schemes exist in the academic literature but are not yet production-ready.

**Option 3 — Hierarchical PRE**: Alice delegates to Carol, Carol delegates to Bob. Each delegation creates a separate re-encryption level. This introduces transitivity, which is a security consideration (Blaze-Bleumer-Strauss transitivity attack).

**Option 4 — Shared secret with PRE**: Alice and Carol each encrypt their share of a split DEK. Bob must collect re-encrypted DEK shares from both owners' proxy chains and XOR them (or use Shamir reconstruction) to get the full DEK.

For the prototype, single-owner delegation (Alice → Bob) is implemented. Multi-owner would require significant protocol extensions.

### Q24. What cryptographic assumptions does this system rely on?

**Answer:**

The security of the system rests on the following hardness assumptions:

1. **ECDLP (Elliptic Curve Discrete Logarithm Problem)**: Given `g` and `g^x`, it is computationally infeasible to find `x`. This underlies Umbral key security.

2. **DBDH (Decisional Bilinear Diffie-Hellman)**: Given `(g, g^a, g^b, g^c, T)`, it is infeasible to decide whether `T = e(g,g)^{abc}` or `T` is random. The AFGH PRE CCA-security proof reduces to DBDH.

3. **AES PRF security**: AES is a secure pseudorandom permutation. No polynomial-time adversary can distinguish AES-256 output from a random permutation.

4. **GCM MAC security**: GHASH is a secure polynomial MAC over GF(2^128). Tag forgery probability is ≤ (l+1)/2^128 for a message of `l` blocks.

5. **Random Oracle Model**: The hash functions H and KDF used in Umbral are modelled as random oracles in the security proof. Real-world instantiations use HKDF-SHA256.

6. **Shamir Secret Sharing information-theoretic security**: For t-1 shares, no computationally unbounded adversary can determine the secret. This is unconditional, not computational.

**Post-quantum status**: Assumptions 1 and 2 are broken by Shor's algorithm on a sufficiently powerful quantum computer. AES-256 retains ~128 bits of quantum security (Grover's algorithm halves effective key length).

### Q26. What is the difference between capsule re-encryption and traditional re-encryption?

**Answer:**

| Aspect | Traditional Re-Encryption | Capsule Re-Encryption (PRE) |
|---|---|---|
| Input to proxy | `Enc(pk_A, m)` = full ciphertext, proxy decrypts m first | Capsule `(E, V, s)` only — tiny fixed-size header |
| Proxy knowledge | Proxy must know `sk_A` to decrypt | Proxy knows only `kfrag_i`, never `sk_A` or `m` |
| Plaintext exposure | Proxy sees `m` | Proxy never sees `m` |
| Computation | O(|m|) for proxy (must decrypt+encrypt full payload) | O(1) for proxy (operates on 3 EC points) |
| Key distribution | Proxy needs `sk_A` — catastrophic if proxy is compromised | Proxy needs only `kfrag_i` — limited blast radius |
| Output size | `Enc(pk_B, m)` — same as input | Capsule fragment — fixed size regardless of `m` |

Capsule re-encryption is strictly superior in all security-relevant dimensions, with the proxy seeing less information and performing less work.

### Q28. What happens if fewer than threshold cfrags are available?

**Answer:**

If Bob attempts `decrypt_reencrypted` with fewer than `t=2` valid cfrags, the Umbral library raises an error. The Lagrange interpolation requires exactly `t` distinct evaluation points; with fewer, the system cannot reconstruct the re-encrypted capsule point.

**In the proxy service**:
```python
def reencrypt_with_workers(capsule_b64, kfrags_b64_list, threshold=2):
    cfrags = []
    for i, kfrag in enumerate(kfrags_b64_list):
        try:
            cfrag = proxy_reencrypt_capsule(capsule_b64, kfrag)
            cfrags.append({"worker_id": i+1, "cfrag_b64": cfrag, "status": "success"})
        except Exception as e:
            cfrags.append({"worker_id": i+1, "status": "failed", "error": str(e)})

    successful = [c for c in cfrags if c["status"] == "success"]
    if len(successful) < threshold:
        raise ValueError(f"Insufficient cfrags: {len(successful)} < threshold {threshold}")
```

**Demo scenario**: Kill Proxy Workers 1 and 2, attempt re-encryption → `InsufficientCfrags` error. This demonstrates the threshold fault boundary.

### Q29. How does the system prevent replay attacks?

**Answer:**

Replay attacks involve capturing a valid re-encryption request and replaying it later to obtain cfrags after access has been revoked.

**Mitigations in the prototype**:
1. **Grant status check**: Each re-encryption call checks `grant.status == 'active'`. After revocation, replaying the request still returns `403 Forbidden`.
2. **Audit log**: Every re-encryption request is logged with timestamp, user ID, IP address, and grant ID. Unusual patterns (many requests in short time) can be detected.

**Limitations**:
- No nonce or timestamp in re-encryption requests in the prototype.
- If a request is captured before revocation and replayed during the same active window, it succeeds (as intended behavior).

**Production mitigations**:
- Include a request timestamp and nonce in all API calls.
- Reject requests with timestamps outside a ±5 minute window.
- Track used nonces in a Redis cache (short TTL) to prevent exact replay.
- Use request signing (HMAC or JWT with short expiry).

### Q30. What is the academic significance of this implementation?

**Answer:**

This implementation demonstrates several academically significant concepts:

1. **Practical PRE**: Prior to systems like NuCypher and pyUmbral, PRE was largely theoretical. This prototype shows that the Umbral scheme is practical for real workloads, with sub-10 ms overhead for the cryptographic re-encryption operations.

2. **Threshold security in practice**: The 2-of-3 threshold demonstrates that academic Shamir secret sharing directly maps to practical distributed proxy deployment, achieving both fault tolerance and compromise resistance.

3. **Hybrid encryption architecture**: The AES + PRE combination demonstrates the standard hybrid pattern that underlies all production-grade public key encryption systems, applied to a novel PRE context.

4. **IoT security model**: The system formalizes the IoT data sharing threat model — differentiating between data confidentiality (AES), key delegation security (PRE), and access control (grant management) — as separate but composable layers.

5. **Performance validation**: The benchmarks empirically confirm the theoretical O(1) PRE overhead claim, providing concrete numbers that can be cited in comparative analyses.

6. **Security property composition**: The system demonstrates that confidentiality (AES), integrity (GCM tag), authenticity (kfrag signing), and access control (grant authorization) can be composed into a coherent, formally analyzable security architecture.

The project provides a reproducible baseline for future research into post-quantum PRE, attribute-based PRE, and multi-party IoT data sharing protocols.
